# @supporters/api

The Fastify 5 backend for web and mobile. Spec: [`docs/specs/backend-spec.md`](../../docs/specs/backend-spec.md).

## Local setup

Needs Node 24 and Docker.

```bash
pnpm install
cd apps/api
docker compose up -d            # PostgreSQL 18, Valkey 9, MinIO (S3)
cp .env.example .env
pnpm --silent keys:generate >> .env   # JWT signing key and OTP HMAC key
pnpm db:deploy                  # apply migrations
pnpm storage:init               # media bucket in MinIO
pnpm db:seed                    # states, cities, placeholder categories, two demo users
pnpm dev                        # http://127.0.0.1:3001
```

If ports 5432, 6379 or 9000 are taken, start compose with `POSTGRES_PORT=55432 VALKEY_PORT=56379 MINIO_PORT=59000` and change the URLs in `.env` to match.

Uploads go straight from the client to S3 (MinIO locally): `POST /v1/uploads/presign` returns a 5-minute PUT URL locked to the declared type and size, then `POST /v1/uploads/:id/complete` checks the stored file's size and magic bytes. Image re-encoding (sharp, EXIF stripping) is still a stub, `PassthroughMediaProcessor`, and the API refuses to start in production with it. On a phone, `localhost:9000` is not reachable; point `S3_ENDPOINT` and `MEDIA_PUBLIC_URL` at your machine's LAN address.

OTPs print to the terminal (`[dev sms] ...`); MSG91 replaces this on staging and production.

## Scripts

| Script                 | What it does                                                                      |
| ---------------------- | --------------------------------------------------------------------------------- |
| `dev`                  | Runs `src/server.ts` with tsx in watch mode, reading `.env`                       |
| `test`                 | Vitest. Starts PostgreSQL, Valkey and MinIO in Testcontainers, so Docker must be running |
| `lint`, `typecheck`    | ESLint (strict, type-checked) and `tsc`                                           |
| `db:migrate`           | Creates a migration from `prisma/schema.prisma` changes (development only)        |
| `storage:init`         | Creates the local MinIO bucket and makes its public/ prefix readable |
| `db:deploy`, `db:seed` | Applies migrations; seeds reference data (prisma/reference-data.ts) and demo users |

## Layout

- `src/app.ts` registers the request pipeline in the spec's order: helmet and under-pressure, rate limit (Valkey sliding window), auth, CSRF, Zod validation, then RFC 9457 errors.
- `src/modules/<module>/` holds routes, service and tests. Request and response schemas live in `packages/shared`.
- `src/generated/` is the Prisma client, generated by `prisma generate` (run by `lint`, `typecheck` and `test`) and not committed.

## Messaging in short

- One thread per (user, business); the business side is answered by its owner. `POST /v1/conversations` opens or returns it. An enquiry (`POST /v1/enquiries`) posts into the thread or starts it.
- `POST /v1/conversations/:id/messages` and `POST /v1/enquiries` need an `Idempotency-Key` header (a UUID). It is the message's `clientId`: a retry returns the stored message (200), and the same key with another body is 422 `IDEMPOTENCY_KEY_REUSED`.
- Chat files are private. Upload with purpose `chat`, send the upload ids as `attachmentIds`, and open a file through `GET /v1/attachments/:id`, a redirect to a 5-minute signed URL for the two ends of the thread.
- Blocks work both ways: `PUT/DELETE /v1/blocks/:userId`. The blocked pair cannot message or send enquiries, and the thread is hidden from whoever blocked.

## Auth in short

- Web: `__Host-at` (15 min EdDSA JWT), `__Host-rt` (opaque refresh, rotated on every use) and `__Host-csrf` cookies. Writes echo the CSRF cookie in `x-csrf-token`. `GET /v1/auth/csrf` reissues it.
- Mobile: send `X-Client: mobile`. Login, register and refresh return `{ accessToken, refreshToken, expiresIn }`; send `Authorization: Bearer`.
- Reusing a refresh token more than 10 s after it was rotated revokes the whole session family.

## Notifications in short

- Domain events (`enquiry.created`, `enquiry.replied`, `message.created`, `follow.created`, `post.liked`, `comment.created`, `security.login`, `security.password_changed`) are written to `outbox_events` in the same transaction as the change (`recordEvent` in `src/modules/notifications/outbox.ts`). Payloads hold ids only.
- `NotificationFanout` turns an event into in-app rows and a delivery plan, in one transaction that marks the event processed, so a retried job never doubles a notification. Likes, comments, replies and follows grow one unread row per post or business for 10 minutes; messages grow one row per thread.
- `GET /v1/notifications` (cursor, optional `category`, plus `unreadCount`), `POST /v1/notifications/read` (`{ ids }` or `{ all: true }`), `GET/PUT /v1/me/notification-prefs` (push and email per category; `account` is locked on).

## Verification and reports in short

- An owner asks for the badge with `POST /v1/me/business/verification` (`method` `gstin` or `udyam`, `registrationNumber`, one `certificateUploadId` and one or two `ownerIdUploadIds`, all `kyc` uploads). The business moves to `pending`; one pending request at a time, and a new one only after a rejection. `GET` returns the badge state and the latest request (with the rejection reason).
- `POST /v1/reports` (`targetType` post, comment, message or business, `targetId`, `reason`, optional `details`), 20 a day. Reporting the same target again returns the first report (200). Messages can only be reported by the two ends of the thread, and nobody can report their own content. Review and requirement reports answer 404 until those modules register a target in `ReportTargets`.
- Moderation hides by setting `hidden_at` on posts, comments, messages or businesses. Hidden rows drop out of every public read (`PUBLIC_POST`, `PUBLIC_OWNER`, `PUBLIC_LISTING`, comment lists, chat). A post or comment with 5 open reports from different people is hidden for admin review, and its author gets `content.hidden`.

## Admin in short

- Admins exist only through `pnpm admin:create --phone <+91...> --name <name>` (hidden password prompt). It prints a TOTP enrolment link once for the authenticator app; the secret is stored AES-256-GCM-encrypted with `TOTP_ENCRYPTION_KEY`. `--reset-totp --phone <+91...>` replaces a lost authenticator and signs the admin out everywhere. Admins use a separate account and can't sign in at `/v1/auth/login`.
- `POST /v1/admin/auth/login` `{ identifier, password, code }` (web cookies only) gives an 8-hour `__Host-at` and no refresh token. Each code works once; failures count toward the normal login lockout.
- Every other `/v1/admin/*` route is behind `auth: 'admin'`: a token that passed TOTP, for a session that is live in the database, of an active admin. Anyone else gets 404. Responses are `no-store` and `noindex`. Every admin action, and every admin read, is written to `audit_logs`, which is append-only (a trigger refuses UPDATE and DELETE).
- Suspending a user revokes all their sessions at once (their access tokens stop working immediately) and takes their business, posts and listings out of public reads.

## Worker and delivery

- `pnpm dev:worker` runs `src/worker.ts` (same image as the API, different command: `node dist/worker.js`). It relays the outbox to BullMQ on Valkey, runs the `notifications`, `push`, `email` and `cron` queues (5 attempts, exponential backoff, then the `dead-letter` queue), and cleans up nightly at 03:00 IST (notifications after 90 days, processed outbox rows after 7).
- Push goes to Expo (batches of 100; dead tokens pruned from tickets and receipts) and to Web Push (VAPID; 404/410 subscriptions pruned). Non-urgent push waits out quiet hours (22:00 to 08:00 IST); batched items push once when their 10-minute window ends; security events always go at once. Push payloads hold ids and generic copy only. Email goes only to a verified address (`EMAIL_PROVIDER=ses`, console in dev).
- `POST/DELETE /v1/me/push-tokens`, `POST/DELETE /v1/me/web-push-subscriptions` (known push-service hosts only), `GET /v1/notifications/vapid-public-key`. The worker publishes badge counts on Valkey; the API emits `notification:new { notificationId, unreadCount }` to `user:<id>`.

## Buyer requirements in short

- `POST /v1/buyer-requirements` (any signed-in user): description, category (top level or subcategory), quantity and unit, delivery city, optional budget, up to 3 `requirement` uploads. 3 new per rolling 24 h and 10 open at once. Open for 30 days.
- Matching runs in the worker: `requirement.created` goes through the outbox, and its fan-out job writes `requirement_matches` (same top-level category, active owner, no block, and the business is in the delivery city or a published listing ships to or serves it). The best 50 verified businesses, Premium first, get a `requirement.matched` notification.
- `GET /v1/buyer-requirements` is the Requirements list of the signed-in user's business (open, matched, newest first; the first item is the pinned feed card). `GET /v1/buyer-requirements/:id` is open to the buyer and matched businesses only. `GET /v1/me/buyer-requirements?status=` is the buyer's own list; `PATCH /v1/buyer-requirements/:id` closes or fulfils.
- The `cron` queue flips open requirements past `expires_at` to `expired` every hour; reads already treat them as expired.
