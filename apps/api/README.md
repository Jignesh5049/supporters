# @supporters/api

The Fastify 5 backend for web and mobile. Spec: [`docs/specs/backend-spec.md`](../../docs/specs/backend-spec.md).

## Local setup

Needs Node 24 and Docker.

```bash
pnpm install
cd apps/api
docker compose up -d            # PostgreSQL 18, Valkey 9, MinIO (S3)
cp .env.example .env
pnpm --silent keys:generate >> .env   # JWT signing key and OTP HMAC key
pnpm db:deploy                  # apply migrations
pnpm storage:init               # media bucket in MinIO
pnpm db:seed                    # states, cities, placeholder categories, two demo users
pnpm dev                        # http://127.0.0.1:3001
```

If ports 5432, 6379 or 9000 are taken, start compose with `POSTGRES_PORT=55432 VALKEY_PORT=56379 MINIO_PORT=59000` and change the URLs in `.env` to match.

Uploads go straight from the client to S3 (MinIO locally): `POST /v1/uploads/presign` returns a 5-minute PUT URL locked to the declared type and size, then `POST /v1/uploads/:id/complete` checks the stored file's size and magic bytes. Image re-encoding (sharp, EXIF stripping) is still a stub, `PassthroughMediaProcessor`, and the API refuses to start in production with it. On a phone, `localhost:9000` is not reachable; point `S3_ENDPOINT` and `MEDIA_PUBLIC_URL` at your machine's LAN address.

OTPs print to the terminal (`[dev sms] ...`); MSG91 replaces this on staging and production.

## Scripts

| Script                 | What it does                                                                      |
| ---------------------- | --------------------------------------------------------------------------------- |
| `dev`                  | Runs `src/server.ts` with tsx in watch mode, reading `.env`                       |
| `test`                 | Vitest. Starts PostgreSQL, Valkey and MinIO in Testcontainers, so Docker must be running |
| `lint`, `typecheck`    | ESLint (strict, type-checked) and `tsc`                                           |
| `db:migrate`           | Creates a migration from `prisma/schema.prisma` changes (development only)        |
| `storage:init`         | Creates the local MinIO bucket and makes its public/ prefix readable |
| `db:deploy`, `db:seed` | Applies migrations; seeds reference data (prisma/reference-data.ts) and demo users |

## Layout

- `src/app.ts` registers the request pipeline in the spec's order: helmet and under-pressure, rate limit (Valkey sliding window), auth, CSRF, Zod validation, then RFC 9457 errors.
- `src/modules/<module>/` holds routes, service and tests. Request and response schemas live in `packages/shared`.
- `src/generated/` is the Prisma client, generated by `prisma generate` (run by `lint`, `typecheck` and `test`) and not committed.

## Messaging in short

- One thread per (user, business); the business side is answered by its owner. `POST /v1/conversations` opens or returns it. An enquiry (`POST /v1/enquiries`) posts into the thread or starts it.
- `POST /v1/conversations/:id/messages` and `POST /v1/enquiries` need an `Idempotency-Key` header (a UUID). It is the message's `clientId`: a retry returns the stored message (200), and the same key with another body is 422 `IDEMPOTENCY_KEY_REUSED`.
- Chat files are private. Upload with purpose `chat`, send the upload ids as `attachmentIds`, and open a file through `GET /v1/attachments/:id`, a redirect to a 5-minute signed URL for the two ends of the thread.
- Blocks work both ways: `PUT/DELETE /v1/blocks/:userId`. The blocked pair cannot message or send enquiries, and the thread is hidden from whoever blocked.

## Auth in short

- Web: `__Host-at` (15 min EdDSA JWT), `__Host-rt` (opaque refresh, rotated on every use) and `__Host-csrf` cookies. Writes echo the CSRF cookie in `x-csrf-token`. `GET /v1/auth/csrf` reissues it.
- Mobile: send `X-Client: mobile`. Login, register and refresh return `{ accessToken, refreshToken, expiresIn }`; send `Authorization: Bearer`.
- Reusing a refresh token more than 10 s after it was rotated revokes the whole session family.

## Notifications in short

- Domain events (`enquiry.created`, `enquiry.replied`, `message.created`, `follow.created`, `post.liked`, `comment.created`, `security.login`, `security.password_changed`) are written to `outbox_events` in the same transaction as the change (`recordEvent` in `src/modules/notifications/outbox.ts`). Payloads hold ids only.
- `NotificationFanout` turns an event into in-app rows and a delivery plan, in one transaction that marks the event processed, so a retried job never doubles a notification. Likes, comments, replies and follows grow one unread row per post or business for 10 minutes; messages grow one row per thread.
- `GET /v1/notifications` (cursor, optional `category`, plus `unreadCount`), `POST /v1/notifications/read` (`{ ids }` or `{ all: true }`), `GET/PUT /v1/me/notification-prefs` (push and email per category; `account` is locked on).
